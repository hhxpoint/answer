# 小火苗延迟与流畅度优化记录

> 目标：不改变功能，降低悄悄话发送/接收与聊天打开的延迟，提升流畅度。
> 记录时间：2026-11-18。状态：服务端已部署；客户端 1.31.0 待重新上传（当前网络 IP 不在上传白名单）。

## 1. 实测瓶颈

| 链路 | 实测 |
|---|---|
| 服务器位置 | Azure 美国西部（Moses Lake, WA） |
| 服务器本机 `/health` | 0.5–0.9ms |

## 2. 本次优化（已实现）

### 客户端
- **乐观发送**：点击发送立即出现「发送中」气泡，输入框立即清空；服务端返回后替换为正式消息，失败可点击重试。
- **幂等键**：每条消息生成 `client_msg_id`，重试不会重复；WS/HTTP 同时返回时按幂等键去重。
- **本地缓存**：按空间缓存最近 50 条消息，进入聊天先显示缓存，再后台刷新。
- **并行加载 + WS 预连接**：`me` 与最近消息并行，WS 提前连接；在线时停止 8s 全量轮询。
- **增量渲染/滚动**：只更新变化的消息数据，发送后立即滚动到底部。

### 服务端
- **消息幂等**：`messages.client_msg_id` + 部分唯一索引；重复请求直接返回已存在消息（不再等内容安全）。
- **内容安全缓存**：相同文本 + openid 的「通过」结果缓存 2 分钟（LRU 500 条）。
- **内容安全超时预算**：`msgSecCheck` 800ms 超时，超时沿用现有“异常放行”策略，避免微信接口抖动卡死消息。
- **微信 API 连接复用**：`https.Agent({keepAlive:true})`，避免每次重建 TLS。
- **时序观测**：慢请求（>800ms）与消息内容安全耗时写入日志，便于后续对比。

### 数据迁移
- `messages.client_msg_id` 加法式迁移 + 唯一索引；迁移记录 `003_chat_idempotency`。
- 迁移前备份：`backups/pre-latency-*.db`；迁移后数据量一致。
